## Summary

承認済みの計画にある独立したタスクを、ホスト標準のサブエージェントに分担させて並列に実装する。進め方は 3 段階で、まず親(リード)エージェントが進捗ボードを起動し、次に `tasks/PLAN.md` の先頭から並列に進められるタスクを選んでサブエージェントに渡し、最後に各サブエージェントがボードの API と SSE につないで自分のタスクの進捗を共有し、コメントをリアルタイムに受け取る。

## Problem and outcome

- 計画には並列グループがあるのに、実装は 1 タスクずつ順番に進んでいた。並列に進められるタスクがあっても、待ち時間が積み重なる。
- 並列に進める場合、どのタスクを同時に始めてよいかを人やエージェントがその場で判断すると、依存関係やファイルの担当範囲を見落としやすい。
- 複数のエージェントが同時に動くと、誰がどのタスクで何をしているのかが見えない。ユーザーのフィードバックも、担当のエージェントに確実に届く経路がない。

これにより、始めてよいタスクは計画から機械的に決まり、サブエージェントはそれぞれ独立した worktree で同時に進む。各タスクの進捗はボードで見え、ユーザーのコメントはそのタスクを担当するサブエージェントへ投稿と同時に届く。

## Target users

- Smartpowers で複数タスクの計画を実装するユーザー
- タスクを割り振って統合するリードエージェントと、1 タスクを実装するサブエージェント

## Scope

### In scope

- 今すぐ開始できるタスクを返すコマンド `board next`
- リードとサブエージェントの手順と、サブエージェントへのブリーフ(`SKILL.md`)
- 起動中のボードへのエージェント接続(トークン認証の API と、タスク単位の SSE)
- 接続中のエージェントをボードに表示すること
- ボードが起動していないときの、ファイル経由のフォールバック

### Out of scope

- サブエージェントを起動する仕組みそのもの(ホスト標準の機能を使う)
- ブランチの自動マージ(リードが手順に沿って行う)
- 独立したプロセスとして `claude -p` / `codex exec` を起動するオーケストレーター
- ボード上でタスクの状態を変更すること(状態はタスクファイルが正)

## Functional requirements

| ID | Priority | Requirement | Acceptance criteria |
| --- | --- | --- | --- |
| REQ-001 | Must | `board next --project <id>` は、`tasks/PLAN.md` の実行順に沿って、今すぐ開始できるタスクを返す。開始できるのは、状態が `Planned` で依存がすべて `Done` のタスクである。 | PLAN.md でタスク番号と異なる順序を指定すると、その順序で返る。依存が未完了のタスクは返らない。 |
| REQ-002 | Must | 同時に開始するのは同じ並列グループのタスクだけとする。実行中のタスクがなければ、先頭の準備済みタスクと同じグループのタスクを返す。実行中のタスクがあれば、そのグループのタスクだけを追加する。並列グループのないタスクは単独で実行する。 | 実行中がグループ A なら、グループ A のタスクだけが返る。グループなしのタスクが実行中なら、何も返らない。 |
| REQ-003 | Must | 開始できるタスクがないときは、その理由を示す(すべて完了、依存待ち、ブロック中のタスク、実行中のタスクの完了待ち)。 | 結果が空のとき、出力に理由が 1 行で書かれている。 |
| REQ-004 | Should | `--limit <n>` で、一度に開始するタスクの数を制限できる。 | `--limit 1` で 1 件だけ返る。0 以下の値はエラーになる。 |
| REQ-005 | Must | リードは、返された各タスクの状態を `In Progress` にしてから、タスクごとに 1 つのサブエージェントを、それぞれ独立した git worktree で同じターンに起動する。手順は `SKILL.md` に定義する。 | `SKILL.md` の Parallel execution に、worktree での隔離と同時起動の手順が書かれている。 |
| REQ-006 | Must | サブエージェントへのブリーフには、プロジェクト ID、`--root` に使うメインチェックアウトの絶対パス、ボードの起動スクリプトのパス、タスクファイルの全文、依存、並列グループ、担当ファイル、検証コマンド、守るべきルールを含める。 | `SKILL.md` のブリーフ項目に、これらがすべて挙がっている。 |
| REQ-007 | Must | タスクの状態、`PLAN.md`、Linear を更新するのはリードだけとする。サブエージェントは自分の worktree の担当ファイルだけを変更して commit し、push しない。 | `SKILL.md` に、リードだけが更新すること、サブエージェントに禁止することが明記されている。 |
| REQ-008 | Must | リードは、終わったサブエージェントのブランチをマージして検証し、成功なら `Done`、失敗や衝突なら `Blocked` にして理由をログに残し、もう一度 `board next` を実行する。 | `SKILL.md` に、統合、状態の更新、繰り返しの手順が書かれている。 |
| REQ-009 | Must | サブエージェントは `board inbox --task <NN> --wait` で起動中のボードにつなぎ、自分のタスクへのコメントを投稿と同時に受け取る。ほかのタスクへのコメントは受け取らない。 | 2 つのサブエージェントが接続しているとき、タスク 07 へのコメントは 07 の担当にだけ届き、06 の担当は待ち続ける。 |
| REQ-010 | Must | サブエージェントが `board log` で書いた進捗は、ボードのタスクの Activity とカードに表示される。 | ログを書くと、リロードせずにボードへ反映される。 |
| REQ-011 | Should | エージェントが接続しているタスクのカードには Agent バッジを出し、全タスクを聞いているリードがいればヘッダに表示する。接続が切れたら消す。 | 接続中はバッジが出て、切断すると数秒で消える。 |
| REQ-012 | Must | ボードが起動していないときも、`inbox`、`reply`、`log` は状態ディレクトリのファイルを直接読み書きして動く。 | ボードを止めた状態で、3 つのコマンドがエラーなく動き、結果が後でボードに表示される。 |

## Non-functional requirements

| ID | Area | Requirement | Measure |
| --- | --- | --- | --- |
| NFR-001 | Security | エージェント用 API は、起動ごとに生成したランダムなトークンを必須にする。トークンは所有者だけが読めるファイルに置き、ブラウザからは使えない。 | トークンなし、または誤ったトークンの要求は 401 になる。Unix ではファイルの権限が 0600 である。 |
| NFR-002 | Latency | コメントはポーリングではなくプッシュで届ける。 | 投稿からサブエージェントの `inbox` が受け取って終了するまでが 5 秒未満(テストで検証)。 |
| NFR-003 | Reliability | 購読を始めてから保留中のコメントを読み込むまでの間に、コメントの取りこぼしや重複配信が起きない。 | 購読を先に登録し、配信済みの ID で重複を除いている。保留中のコメントは接続直後に必ず届く。 |
| NFR-004 | Liveness | 接続が切れたら、ボードの接続表示は速やかに消える。 | 切断から約 5 秒以内にバッジが消える。 |

## User journeys

1. ユーザーが実装を始めるよう頼む。リードはボードを起動し、`board next` で 06 と 07(どちらもグループ D)を受け取る。
2. リードは 06 と 07 を `In Progress` にして、それぞれのサブエージェントを worktree で起動する。ボードには 2 枚のカードに Agent バッジが付き、ログが流れはじめる。
3. ユーザーが 07 に「スクロールは panel-scroll 側で直して」とコメントする。07 のサブエージェントだけがすぐに受け取って方針を変え、返信する。
4. 両方が終わると、リードがマージして検証し、`Done` にして、もう一度 `board next` を実行する。

## Assumptions and constraints

- ホストにはサブエージェントの機能がある(Claude Code の Agent ツールなど)。worktree での隔離はホストの機能か `git worktree add` で行う。
- 並列グループは計画段階で、依存関係がなく担当ファイルも重ならないタスクにだけ付けられている(planning ガイドに従う)。
- コメントとログ、ボードの接続情報は、メインチェックアウトを基準にした状態ディレクトリにある。worktree を `--root` にすると別の場所を指してしまう。
- サブエージェントがバックグラウンドのコマンドの完了通知を受け取れない環境では、各ステップのあとに `--wait` なしの `inbox` を実行して代わりとする。

## Success measures

- 並列グループを持つ計画で、同じグループのタスクが同時に進む。
- 各タスクへのコメントが、担当のサブエージェントに数秒以内で届き、返信される。

## Risks

- 実際の Claude Code の Agent ツールでサブエージェントを起動しての運用は、まだ検証していない。検証済みなのは、CLI を手動で実行してサブエージェントの動きを再現したところまでである。
- サブエージェントがバックグラウンドの待ち受けを維持し続けるか、また完了の通知を受け取れるかは、ホストによって異なる可能性がある。
- 並列グループの付け方を誤ると、同じファイルを同時に変更してマージで衝突する。

## Open questions

- Claude Code のサブエージェントは、バックグラウンドのコマンドの完了通知を作業の途中で受け取れるか。受け取れなければ、各ステップ後に確認する代替手順を主とするべきか。
- Codex で同じ手順が成り立つか(サブエージェントの機能と worktree での隔離)。
