# Product Requirements Document

Status: Draft
Last updated: 2026-10-18
Project: 20261018-011340-parallel-review-pr

## Summary

並列実行で、サブエージェントが終えた各タスクを、ユーザーが Crit でコードレビューしてから取り込むようにする。承認されたタスクのブランチは push して Pull Request にし、マージはユーザーが GitHub で行う。リードはマージを確かめてからタスクを `Done` にし、次のタスクへ進む。

## Problem and outcome

- 今の並列実行の手順では、リードがサブエージェントのブランチをローカルでマージし、検証が通ればそのまま `Done` にする。Crit が出てくるのは最後の push のときだけなので、タスクごとのコードレビューが抜け落ちる。実際に、レビューなしで取り込まれたことがあった。
- タスクごとに worktree とブランチを切っているのに、PR にしていない。そのため、変更をタスク単位で見たり、CI を通したり、履歴を追ったりできない。

これにより、並列に実装されたタスクも、すべてユーザーのレビューと承認を経てから取り込まれる。各タスクは 1 つの PR として残る。

## Target users

- 並列実行で Smartpowers の計画を実装するユーザー(レビューしてマージする人)
- サブエージェントの成果を統合するリードエージェント

## Scope

### In scope

- `SKILL.md` の Parallel execution の手順の変更(Crit レビュー、push、PR の作成、マージ待ち、`Done` にする条件)
- タスクファイルへの PR の記録と、ボードでの PR のリンク表示
- `gh` やリモートを使えないときの代替手順

### Out of scope

- PR をエージェントが自動でマージすること
- 並列でない、1 タスクずつの実装を PR にすること(今の手順のまま)
- サブエージェント自身による push や PR の作成(今までどおり、push はリードだけが行う)
- GitHub 以外のホスティング(GitLab の MR など)
- 着手するタスクの選び方と、実行計画のフローチャート(execution-flowchart プロジェクト)

## Functional requirements

| ID | Priority | Requirement | Acceptance criteria |
| --- | --- | --- | --- |
| REQ-001 | Must | サブエージェントが終わったら、リードはタスクの検証をそのブランチで実行し、通ったら、そのブランチの差分(作業ブランチからの分岐点から先)を Crit でユーザーのレビューに出す。Crit のレビューを経ずにタスクを取り込んだり、`Done` にしたりしない。 | `SKILL.md` の手順で、Crit のレビューが push、PR、`Done` のすべてより前にあり、省略してよい場面が書かれていない。 |
| REQ-002 | Must | レビューにコメントがあれば、リードはそのタスクのブランチで直す(またはサブエージェントに戻す)。直したら、もう一度 Crit で開く。`approved: true` で終わるまで繰り返す。 | `SKILL.md` に、指摘の反映とレビューのやり直しの手順がある。 |
| REQ-003 | Must | Crit でタスクのブランチが承認されたら、それをそのブランチの push の承認とみなす。リードはブランチを push し、作業ブランチを向き先にして `gh pr create` で PR を作る。承認のあとでコミットを足したり書き換えたりしたら、もう一度レビューを受ける。 | `SKILL.md` の Push approval と Parallel execution に、タスクのブランチについてのこの扱いが書かれている。承認した範囲の外のコミットは push されない。 |
| REQ-004 | Must | PR の本文には、プロジェクト ID、タスク番号とタイトル、要件 ID、変更の要約、検証の結果を書く。 | `SKILL.md` に PR の本文の項目が挙がっている。 |
| REQ-005 | Must | リードは PR の URL を、タスクファイルの `Pull request:` の行と `board log` に記録する。Linear につないでいれば、そこにもリンクする。 | PR を作ったあとのタスクファイルに `Pull request: <URL>` がある。 |
| REQ-006 | Must | マージはユーザーが GitHub で行う。PR を作ったタスクは、マージされるまで `In Progress` のままにする。リードはマージを確かめたら作業ブランチを更新し、検証してから `Done` にする。 | `SKILL.md` に、マージの確かめ方(`gh pr view` の状態)、更新、`Done` にする条件が書かれている。マージ前の PR のタスクは `Done` にならない。 |
| REQ-007 | Must | 閉じられた(マージされずに終わった)PR や、マージ後の検証の失敗は、`Blocked` にして理由をログに残す。 | `SKILL.md` に、その場合の扱いが書かれている。 |
| REQ-008 | Must | 同時に走っていた複数のタスクが終わったら、Crit のレビューはタスクごとに分けて出す。PR もタスクごとに 1 つにする。後続のタスクは、依存先の PR がマージされた作業ブランチから始める。 | `SKILL.md` に、タスクごとのレビューと PR、後続を始める条件が書かれている。 |
| REQ-009 | Must | Crit がなければ、ブランチのコミットの一覧と `git diff --stat` をチャットで示して、明示の承認を得る。`gh` かリモートがなければ、承認のあとにローカルでマージする今の手順に戻り、そのことをユーザーに伝える。 | `SKILL.md` に、この 2 つの代替手順が書かれている。 |
| REQ-010 | Should | ボードは、タスクの `Pull request:` を読み、カード、リストの行、詳細パネルに PR のリンクを表示する。 | `Pull request:` のあるタスクで、3 か所に PR のリンクが出る。 |
| REQ-011 | Should | 計画ガイドのタスクファイルの書式に `Pull request:` の欄を加え、検証スクリプトはこの欄があっても通す。 | 計画ガイドに欄がある。欄のあるタスクファイルで `--phase implementation` の検査が通る。 |

## Non-functional requirements

| ID | Area | Requirement | Measure |
| --- | --- | --- | --- |
| NFR-001 | Safety | push は、Crit かチャットでユーザーが承認した、そのタスクのブランチのコミットだけに限る。force-push はしない。 | 手順上、承認と push の範囲が一致し、force-push の指示がない。 |
| NFR-002 | Ownership | 今までどおり、タスクの状態、`PLAN.md`、Linear を変えるのはリードだけで、サブエージェントは push しない。 | サブエージェントへのブリーフの規則が変わっていない。 |
| NFR-003 | Visibility | レビュー待ちとマージ待ちの間も、ボードでそれとわかる。 | リードがレビューを出したとき、PR を作ったとき、マージを確かめたときに `board log` が残る。 |

## User journeys

1. 同時に走っていた 02 と 03 のサブエージェントが終わる。リードは 02 の検証を通し、Crit で 02 の差分を開く。ユーザーは 1 件コメントし、リードが直して開き直すと、ユーザーは承認する。
2. リードは 02 のブランチを push して PR を作り、URL をタスクファイルとボードに残す。続いて 03 も同じ流れでレビューに出す。
3. ユーザーが GitHub で 02 と 03 の PR をマージする。リードはマージを確かめて作業ブランチを更新し、検証してから 2 つを `Done` にして、それらに依存していたタスクに着手する。

## Assumptions and constraints

- リポジトリには GitHub のリモートがあり、`gh` で認証できている。そうでない場合は REQ-009 の代替手順をとる。
- PR の向き先は、リードが作業しているブランチ(多くは `main`)とする。
- Crit のレビューは、タスクのブランチの範囲を `crit --range` で開く。範囲の取り方の詳細は設計で決める。
- タスクの状態は今の 4 つ(Planned / In Progress / Blocked / Done)のまま増やさない。レビュー待ちとマージ待ちは、`In Progress` とログで表す。

## Success measures

- 並列実行で取り込まれたすべてのタスクに、Crit の承認の記録と、マージされた PR がある。
- `Done` のタスクのうち、PR がマージされていないものがない(代替手順をとった場合を除く)。

## Risks

- マージをユーザーが行うので、PR が溜まると後続のタスクに着手できず、並列化の効果が下がる。
- 同時に走ったタスクの PR を順にマージすると、後の PR が衝突することがある。依存のないタスクは担当ファイルが重ならないよう計画するが、ロックファイルなどの共有ファイルで起きうる。
- ボードの変更(REQ-010)は、execution-flowchart プロジェクトと同じ UI のファイルに触れる可能性がある。実装の順番を調整する必要がある。
