## Summary

進捗ボードを、ユーザーが作業中のエージェントを途中で軌道修正できる場にする。ユーザーはタスク詳細からコメントを送り、実装中のエージェントは作業の途中でそれを受け取って方針を直し、返信する。エージェントはタスクごとに進捗ログを残し、ボードの Activity 欄でコメントと並べて時系列に見られるようにする。

## Problem and outcome

- 0.5.0 までのボードは読み取り専用だった。エージェントの作業が意図とずれていると気づいても、チャットに戻って割り込むしかなく、どのタスクについての指摘かも伝わりにくい。
- エージェントが今何をしているかは、タスクファイルの `Status:` からしか分からなかった。
- 指示を作業の最後にまとめて受け取ると、ずれたまま作業が進み、手戻りが大きくなる。

これにより、ユーザーはタスク単位でその場でフィードバックでき、エージェントは作業中に受け取って直せる。進捗と対応状況は、ボード上の一つの時系列で追える。

## Target users

- 実装中のエージェントの様子をボードで見ているユーザー
- Smartpowers の手順に沿ってタスクを実装するエージェント(Claude Code / Codex)

## Scope

### In scope

- タスク詳細でのコメントの作成と送信
- エージェント向けの CLI: `board inbox`(新しいコメントの受け取り)、`board reply`(返信と対応済み化)、`board log`(進捗ログ)
- コメントの配信状態の表示と、スレッドの表示
- Activity 欄(ログとコメントの時系列)と、進行中カードへの最新ログの表示
- コメントとログを、リポジトリの外の状態ディレクトリに保存すること
- SKILL.md の「Board feedback loop」の手順

### Out of scope

- 起動中のボードの API や SSE を通じて、コメントを即時に届けること、タスク単位で購読すること、接続中のエージェントを表示すること。これらは後続プロジェクト `20261017-210654-parallel-subagents`(0.7.0)で拡張する。
- ユーザー同士のコメントのやり取り、コメントの編集と削除、ボードからユーザーがコメントを対応済みにする操作
- コメントやログを git で管理すること
- ボードからタスクの状態を変更すること(ボードはリポジトリのファイルを変更しない)

## Functional requirements

| ID | Priority | Requirement | Acceptance criteria |
| --- | --- | --- | --- |
| REQ-001 | Must | タスク詳細のコメント欄に本文を入力して送信できる。⌘/Ctrl+Enter でも送信できる。 | 送信すると欄が空になり、Activity にコメントが追加される。空のコメントや 8,000 文字を超えるコメントは理由を表示して拒否する。 |
| REQ-002 | Must | 実装中のエージェントは、作業を止めずに新しいコメントを受け取れる。 | バックグラウンドで `board inbox --wait` を実行しているエージェントに、送信から数秒以内にコメントが届く。届いたコメントにはタスク番号、タイトル、ID、本文が含まれる。 |
| REQ-003 | Must | 各コメントは、エージェントに 1 回だけ届く。 | `board inbox` が一度表示したコメントは、次の `board inbox` では表示されない(「No new comments」になる)。 |
| REQ-004 | Must | エージェントはコメントに返信でき、対応済みにできる。返信はスレッドの最初のコメントにぶら下がる。 | `board reply --comment <id> [--resolve] <message>` を実行すると、返信がスレッドに表示され、`--resolve` を付けた場合は元のコメントが Addressed になる。返信への返信も、スレッドの最初のコメントに付く。 |
| REQ-005 | Must | ユーザーのコメントには、配信状態として Waiting for agent / Sent to agent / Addressed のいずれかを表示する。 | エージェントが受け取るまでは Waiting for agent、受け取ったら Sent to agent、対応済みにしたら Addressed に、画面を再読み込みせずに切り替わる。 |
| REQ-006 | Must | エージェントは、タスクごとに 1 行の進捗ログを記録できる。ログは詳細の Activity 欄に、コメントと合わせて時系列で表示される。 | `board log --task <NN> <message>` のあと、Activity に時刻付きで表示される。存在しないタスクを指定した場合は失敗する。 |
| REQ-007 | Should | 進行中のタスクのカードに、最新の進捗ログを 1 行で表示する。 | In Progress のカードに、最後のログが省略表示で出る。 |
| REQ-008 | Should | 書きかけのコメントは、画面の自動更新やタスクの切り替えで失われない。 | 入力中に変更通知で画面が更新されても、入力内容が残る。別のタスクを開いて戻ると、下書きが戻る。 |
| REQ-009 | Should | 対応待ちのコメントがあるタスクは、カード上で分かる。 | ユーザーのコメントのうち未対応のものの件数が、カードにチップで表示される。 |
| REQ-010 | Must | SKILL.md に、エージェントが守るフィードバックループの手順を定める。手順は、進捗を記録する、受け取りの待機を常に続ける、受け取ったらすぐ対応する、すべてのコメントに返信する、待機を再開する、の 5 つ。 | SKILL.md の「Board feedback loop」節に 5 つの手順がある。承認済みのスコープや設計を変える指摘では承認ゲートに戻ること、コメントを push などの承認の代わりにしないことも明記している。 |

## Non-functional requirements

| ID | Area | Requirement | Measure |
| --- | --- | --- | --- |
| NFR-001 | Security | コメントとログは、リポジトリの外にある、マシンごとの状態ディレクトリに保存する。リポジトリに commit されたファイルが、ユーザーのコメントになりすますことはできない。 | 保存先は `~/.local/state/smartpowers/<repo>-<hash>/`(Windows では `%LOCALAPPDATA%\smartpowers\state`、`SMARTPOWERS_STATE_HOME` で変更可)。テストで、リポジトリ内にファイルが作られないことを確認する。 |
| NFR-002 | Security | コメント投稿の POST は、ループバックの `Origin` ヘッダーを必須とし、ほかのサイトからの投稿を防ぐ。 | `Origin` がない、またはループバック以外の POST は 403 になる(テストで確認)。 |
| NFR-003 | Integrity | 書き込みはアトミックに行い、同じ 1 秒の中で作られたコメントやログの順序も保つ。 | コメントは一時ファイルに書いてから rename で置き換える。時刻はミリ秒まで記録する。返信が元のコメントより前に並ばない(テストを繰り返し実行して確認)。 |
| NFR-004 | Portability | 手順はホスト固有の hook に依存せず、Claude Code と Codex で同じように実行できる。 | 必須の手順が CLI と、バックグラウンドのコマンド実行だけで構成されている。 |
| NFR-005 | Dependencies | Rust の標準ライブラリだけで実装し、新しい依存を追加しない。 | `Cargo.toml` に依存 crate がない。 |

## User journeys

1. ユーザーがボードで進行中のタスク 05 を開き、「件数よりも E2E テストを優先して」とコメントする。表示は Waiting for agent になる。
2. 実装中のエージェントがバックグラウンドで実行していた `board inbox --wait` が終了し、コメントが届く。表示は Sent to agent になる。
3. エージェントは今の編集を終えると方針を変え、`board reply --resolve` で対応内容を返信する。表示は Addressed になり、返信がスレッドに並ぶ。
4. エージェントは `board log` で進捗を記録し、もう一度待機を始める。ユーザーはカードと Activity で進み具合を追う。

## Assumptions and constraints

- コメントを受け取るのは、手順に沿ってバックグラウンドで待機しているエージェントだけである。待機していなければ、コメントは次の `board inbox` まで保留される。
- ボードとエージェントは同じマシンで動く。
- ホストには、バックグラウンドのコマンドが終了したときにエージェントへ通知する機能がある(Claude Code の `run_in_background` など)。

## Success measures

- 送信したコメントが、待機中のエージェントに数秒以内に届く。
- このリポジトリの検証で、コメントの送信、受け取り、返信、対応済み化、ログの記録までを、通しで実行できた。

## Risks

- エージェントが待機を続けないと、コメントは届かない。SKILL.md で待機の再開と、ターン終了前の確認を義務づけている。
- コメントは「ユーザーの指示」として扱われるため、なりすましの経路になりうる。保存先をリポジトリの外にし、POST に Origin を要求して対策する。
