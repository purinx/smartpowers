# Product Requirements Document

Status: Approved
Approved: 2026-10-18 by user
Last updated: 2026-10-17

## Summary

Smartpowers プロジェクトのタスクの進み具合を、ローカルのブラウザに Linear 風のボードで表示する。ボード表示とリスト表示、フェーズの承認状態と進捗、タスクの詳細を見られ、タスクファイルを変更すればリロードしなくても数秒で反映される。

## Problem and outcome

- 進捗を確かめるには、`tasks/` 以下の Markdown を 1 つずつ開くしかなく、全体の状況、依存関係による待ち、担当状況が一目でわからない。
- エージェントが作業している間、ユーザーはチャットの報告を待つしかない。

これにより、ユーザーはブラウザを開いておくだけで、プロジェクトの状態をいつでも把握できる。

## Target users

- Smartpowers で実装フェーズを進めているユーザー
- エージェントの作業をそばで見守りたいユーザー

## Scope

### In scope

- プロジェクトの一覧、ボード表示、リスト表示、フィルタ
- フェーズの承認状態と全体の進捗
- タスクの詳細パネル(属性、Markdown の本文、幅の変更、スクロール)
- リロードなしの更新と、変わったタスクの強調
- キーボード操作、ライト/ダークの配色、狭い画面での表示
- ローカル専用として動かすための安全策と、保守しやすいコード構成

### Out of scope

- ソースからのビルド、配布、Rust ツールチェーンの導入、CI(board-build-from-source プロジェクト)
- タスクへのコメントと進捗ログ(board-feedback-loop プロジェクト)
- エージェント API、`board next`、エージェントの接続表示(parallel-subagents プロジェクト)
- ボードからのタスク状態の変更(状態は今まで通りタスクファイルで管理する)

## Functional requirements

| ID | Priority | Requirement | Acceptance criteria |
| --- | --- | --- | --- |
| REQ-001 | Must | 選んだプロジェクトのタスクを、ステータス別(Planned / In Progress / Blocked / Done)の列に並ぶボード表示と、ステータスごとにまとめたリスト表示の 2 通りで見られる。 | 表示を切り替えても、各タスクがその `Status:` の列やグループに表示される。認識できない状態のタスクがあれば、Other の列が現れる。 |
| REQ-002 | Must | サイドバーに、リポジトリ内の全プロジェクトを新しい順に並べ、それぞれ完了数と総数を添えて表示し、クリックで切り替えられる。 | `docs/smartpowers/projects/` のプロジェクトが、ID の降順に「完了数/総数」付きで並ぶ。 |
| REQ-003 | Must | プロジェクトのヘッダに、PRD・設計・計画の承認状態と、全体の進捗(完了数、総数、割合)を表示する。 | 各成果物の `Status:`(なければ Missing)と進捗バーが、ファイルの内容と一致している。 |
| REQ-004 | Must | 各カードとリストの行に、タスク番号、タイトル、要件 ID、並列グループ、まだ完了していない依存タスク、リモート課題のキー(URL があればリンク)を表示する。 | 依存先がすべて完了しているタスクには、依存待ちの表示がない。 |
| REQ-005 | Must | タスクを選ぶと詳細パネルが開き、属性(状態、要件、依存、並列グループ、リモート課題、ファイルのパス、更新時刻)と、タスクファイル本文の Markdown を表示する。URL でそのタスクを直接開ける。 | `#/<project>/<task>` を開くと、そのタスクのパネルが開いた状態で表示される。依存のチップをクリックすると、依存先のタスクに移る。 |
| REQ-006 | Must | タスクファイルを変更すると、リロードしなくても数秒以内に表示が更新され、変わったタスクが一時的に強調される。 | `Status:` を書き換えると、約 1 秒の監視間隔の範囲で、カードが正しい列に移って強調される。 |
| REQ-007 | Should | キーボードで操作できる(`b` でボード、`l` でリスト、`/` でフィルタ、`Esc` で閉じる)。番号、タイトル、状態、並列グループ、リモートキー、要件 ID でタスクを絞り込める。 | 入力欄にフォーカスがないとき、各キーが動作する。フィルタは大文字と小文字を区別しない。 |
| REQ-008 | Should | 詳細パネルの幅を左端のドラッグで変えられる。幅は覚えておき、ダブルクリックで元に戻せる。キーボードでも変えられる。 | 幅は 320px 以上で、メイン領域が 360px 以上残る範囲に収まる。リロードしても幅が保たれ、ダブルクリックで 520px に戻る。 |
| REQ-009 | Must | 詳細パネルの内容が画面より長いときは、パネルの中でスクロールできる。 | 本文の長いタスクでも、パネルの高さは画面の高さに収まり、中身だけがスクロールする。 |
| REQ-010 | Should | OS のライト/ダーク設定に従い、緑をアクセントにした配色で表示する。スクロールバーはアクセント色の細い線にする。 | OS の設定を切り替えると配色も切り替わる。スクロールバーにカーソルを乗せると、線が太く濃くなる。 |

## Non-functional requirements

| ID | Area | Requirement | Measure |
| --- | --- | --- | --- |
| NFR-001 | Security | ループバックアドレスでだけ待ち受け、Host または Origin がループバック以外のリクエストを拒否する。 | ループバック以外のホストで起動しようとすると失敗する。外部の Host や Origin からのリクエストには 403 を返す(テストで確認)。 |
| NFR-002 | Safety | 表示のためのボードは、リポジトリのファイルを一切変更しない。 | このプロジェクトの範囲のサーバーのコードに、リポジトリへの書き込みがない。 |
| NFR-003 | Accessibility | ライト/ダークの両方で、すべての文字色がコントラスト比 4.5:1 以上(WCAG AA)になる。 | 配色の各組み合わせについて、コントラスト比を計算して確認する。 |
| NFR-004 | Maintainability | UI はビルド工程のない ES モジュールで書き、サーバーは責務ごとのモジュールに分ける。 | 配信されるコードと読むコードが同じである。どのモジュールも単一の責務を持ち、数百行程度に収まる。 |
| NFR-005 | Responsiveness | 幅 900px 以下の画面でも使える。 | 狭い画面では、サイドバーが上に回り、詳細パネルが全画面で開く。 |

## User journeys

1. エージェントが実装を始めると同時にボードを起動し、ユーザーはブラウザで進捗バーとカードの動きを眺める。
2. Blocked の列にカードが現れたので、ユーザーがクリックして詳細を読み、どの依存が未完了なのかを確かめる。
3. 長いタスクの詳細を読むためにパネルを広げ、パネルの中でスクロールして最後まで読む。

## Assumptions and constraints

- タスクファイルは、計画ガイドの書式(`Status:`、`Depends on:`、`Parallel group:`、`Remote task:` などのフィールド)に従っている。
- ボードは、ユーザーのマシンのローカルブラウザから使う。
- サーバーは std のみの Rust で書き、UI はサーバーに埋め込む(ビルドと配布の方式は board-build-from-source で定める)。

## Success measures

- 実装中のプロジェクトで、ユーザーがタスクファイルを開かずに状況を把握できる。
- 状態を変えてから表示に反映されるまでが、数秒以内に収まる。

## Risks

- タスクファイルの書式がずれていると、表示が欠ける。このため、パーサーは寛容に作り、欠けたフィールドは空として扱う。
- 監視間隔(既定 1 秒)のポーリングの負荷は、プロジェクトの規模が大きくなると増える。
