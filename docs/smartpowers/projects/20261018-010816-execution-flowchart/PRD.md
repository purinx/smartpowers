# Product Requirements Document

Status: Draft
Last updated: 2026-10-18
Project: 20261018-010816-execution-flowchart

## Summary

タスクを並列にどの順番で実行するかを、実行計画として `tasks/PLAN.md` に計画と同時に書く。実行計画は、順に進む段(Wave)と、各段で並列に進めるタスクで表す。ボードはこれをフローチャートとして描き、タスクの状態をリアルタイムに重ねて表示する。`board next` も同じ実行計画に従うので、図に描かれた順番と実際の実行順は一致する。

## Problem and outcome

- 今は、実行順が計画のどこにも明示されていない。`board next` が、表の順番、`Depends on`、`Parallel group` からその場で決めている。そのため、計画をレビューするときに「どれとどれが同時に走り、何を待つのか」を頭の中で組み立てる必要がある。
- ボードは状態ごとの列とリストで進捗を見せる。しかし、依存関係の流れの中で今どこまで進んでいて、何が後続を止めているのかは見えない。

これにより、ユーザーは計画のレビューの段階で実行の流れを図で確かめてから承認できる。実装中は、同じ図の上で進み具合とボトルネックを把握できる。

## Target users

- Smartpowers で計画をレビューして承認するユーザー
- 実装中の進捗をボードで見守るユーザー
- `board next` で開始するタスクを決めるリードエージェント

## Scope

### In scope

- `PLAN.md` の実行計画の節(段ごとのタスク)の書式と、計画ガイド、`SKILL.md` への追記
- `validate_workflow.sh --phase plan` による実行計画の検査
- 実行計画に従う `board next`
- ボードのフローチャート表示(依存の矢印、段、状態のライブ表示、クリックで詳細、Draft の計画の表示)

### Out of scope

- ボード上で実行計画やタスクの状態を編集すること(今までどおりファイルが正)
- Mermaid などの外部の図のライブラリや、Markdown の中の図の記法
- 段の自動生成(計画を作るエージェントが、計画ガイドに沿って書く)
- 完了済みの既存プロジェクトの `PLAN.md` に実行計画を書き足すこと

## Functional requirements

| ID | Priority | Requirement | Acceptance criteria |
| --- | --- | --- | --- |
| REQ-001 | Must | `PLAN.md` に実行計画の節を設け、順に進む段と、各段に属するタスク番号を書けるようにする。計画ガイドと `SKILL.md` は、計画の作成と同時にこの節を書くよう指示する。 | 計画ガイドに節の書式と例があり、`SKILL.md` の Phase 3 に、計画と同時に実行計画を書いて承認対象に含める手順がある。 |
| REQ-002 | Must | `validate_workflow.sh --phase plan` は実行計画を検査する。節があること、各タスクがちょうど 1 つの段に属すること、依存先が必ずそれより前の段にあること、2 つ以上のタスクを含む段のタスクが同じ `Parallel group` を持つことを確かめる。 | それぞれの違反を含む計画で検査が失敗し、違反したタスクや段を示すメッセージが出る。正しい計画では成功する。 |
| REQ-003 | Must | 実行計画がある場合、`board next` は段の順に従う。ある段のタスクは、それより前の段のタスクがすべて `Done` になってから開始できる。同じ段のタスクは同時に開始できる。 | 段 1 のタスクがひとつでも `Done` でなければ、段 2 のタスクは返らない。段 1 がすべて `Done` なら、段 2 の `Planned` のタスクがまとめて返る。 |
| REQ-004 | Must | 実行計画に従って開始できるタスクがないとき、`board next` は理由を示す(前の段の完了待ち、ブロック中のタスク、すべて完了など)。 | 結果が空のとき、待っている段と、止めているタスクの番号が 1 行で示される。 |
| REQ-005 | Must | 実行計画のない `PLAN.md`(既存のプロジェクト)では、`board next` は今までの動作を保つ。 | 既存の `board next` のテストがそのまま通る。 |
| REQ-006 | Must | ボードに、ボード表示とリスト表示に並ぶ 3 つ目の表示としてフローチャートを加える。段を左から右へ列として並べ、各タスクをノード、依存を矢印で描く。 | 実行計画のあるプロジェクトで、各タスクが自分の段の列に現れ、`Depends on` の数だけ矢印が描かれる。 |
| REQ-007 | Must | フローチャートのノードは、タスクの状態(Planned / In Progress / Blocked / Done)で見分けがつき、タスクファイルが変わるとリロードなしで更新される。エージェントが接続しているタスクにはその表示を出す。 | `Status:` を書き換えると、約 1 秒の監視間隔の範囲でノードの表示が変わる。接続中のタスクには Agent の表示が出る。 |
| REQ-008 | Must | ノードをクリックすると、既存の詳細パネルが開く。URL で、フローチャートの表示と選んだタスクを直接開ける。 | ノードのクリックで、そのタスクの詳細パネルが開く。URL を開き直すと、同じ表示とパネルが復元される。 |
| REQ-009 | Must | 計画が `Status: Draft` の間もフローチャートを表示し、承認前のレビューに使えるようにする。 | Draft の `PLAN.md` と、`Planned` のタスクファイルだけのプロジェクトで、フローチャートが表示される。 |
| REQ-010 | Should | 実行計画のないプロジェクトでは、`board next` の今の規則(計画の順番と並列グループ)から段を導いて描き、導いた段であることを表示する。 | 完了済みの既存プロジェクトを開くと、フローチャートが描かれ、「導出」の表示が出る。 |
| REQ-011 | Should | 実行計画の節が壊れているとき(存在しないタスク、重複、依存の逆転)は、ボードは表示を止めずに、問題を表示上で示す。 | 不正な実行計画のプロジェクトで、フローチャートの上に警告が出て、ほかの表示は今までどおり動く。 |
| REQ-012 | Should | キーボードでフローチャートに切り替えられる。 | 入力欄にフォーカスがないとき、`f` でフローチャートの表示になる(`b` と `l` は今までどおり)。 |

## Non-functional requirements

| ID | Area | Requirement | Measure |
| --- | --- | --- | --- |
| NFR-001 | Maintainability | 図は外部のライブラリを使わず、ビルド工程のない ES モジュールと SVG で描く。サーバーは std のみの Rust のままにする。 | 新しい依存(npm、CDN、crate)が増えていない。 |
| NFR-002 | Consistency | 実行計画を解釈するのは 1 か所にする。`board next` とフローチャートが同じ解釈の結果を使う。 | 段の割り当ては、サーバーの 1 つのモジュールで計算され、API でフロントへ渡される。 |
| NFR-003 | Scale | 30 タスク程度の計画でも、ノードと矢印が重ならずに読める。 | 30 タスク・8 段の計画で、ノードが重ならない。横にはみ出す分は、表示領域の中でスクロールできる。 |
| NFR-004 | Accessibility | ライト/ダークの両方で、ノードの文字色がコントラスト比 4.5:1 以上になる。状態は色だけでなく、ラベルかアイコンでも区別できる。 | 配色の組み合わせのコントラスト比を計算して確認する。 |
| NFR-005 | Safety | ボードは今までどおり、リポジトリのファイルを変更しない。 | フローチャートの追加で、リポジトリへの書き込みが増えていない。 |

## User journeys

1. エージェントが計画の草案を書き、`PLAN.md` に段 1: 01、段 2: 02 と 03、段 3: 04 の実行計画を入れる。ユーザーはボードのフローチャートで、02 と 03 が並列に走り、04 が両方を待つことを確かめ、03 を段 1 に前倒しするようフィードバックする。
2. 計画が承認され、リードが `board next` で段 1 のタスクを受け取る。フローチャートでは段 1 のノードが In Progress に変わり、Agent の表示が付く。
3. 段 2 の 03 が Blocked になる。ユーザーはフローチャートで、03 が段 3 を止めていることに気づき、ノードをクリックして詳細とログを読む。

## Assumptions and constraints

- 段は、計画を作るエージェントが計画ガイドに沿って書く。並列グループの付け方の規則(依存がなく、担当ファイルが重ならない)は変えない。段は、その並列グループを実行の順番に並べたものにあたる。
- 段の境目では、前の段がすべて `Done` になるまで次の段を始めない(バリア)。先に終わったタスクの後続を早めに始めることはしない。
- 新しく作る計画では、実行計画の節は必須とする。完了済みの既存プロジェクトは検査し直さず、ボードでは導いた段で表示する(REQ-010)。
- 対象は、既存のボード(Rust のサーバーと、埋め込みの ES モジュールの UI)と、bash の検証スクリプトである。

## Success measures

- 計画のレビューで、ユーザーが Markdown の表を読まなくても、並列に走るタスクと待ちの関係をフローチャートで確かめられる。
- 実装中に、図に描かれた順番と `board next` が返すタスクが食い違わない。

## Risks

- バリアを置くと、依存だけで決めるよりも待ち時間が長くなることがある。段の分け方を誤ると、並列化の効果が下がる。
- 実行計画と `Parallel group` の 2 か所に並列の情報があるため、片方だけを直すと食い違う。検査(REQ-002)で防ぐが、ボードの警告(REQ-011)も必要になる。
- 自前のレイアウトでは、矢印の交差が多い計画で図が読みにくくなる可能性がある。
