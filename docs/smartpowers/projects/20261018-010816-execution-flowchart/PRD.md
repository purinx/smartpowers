## Summary

タスクの実行計画を、計画と同時にタスク間の依存関係のグラフとして作る。リードエージェントは、依存がすべて `Done` になったタスクに自分の判断で次々と着手する。決まった段の単位で一斉に進めるのではなく、タスクが 1 つ終わるたびに、新たに着手できるようになったタスクを始める。ボードはこの依存関係のグラフをフローチャートとして描き、タスクの状態と着手できるタスクをリアルタイムに重ねて表示する。`board next` コマンドは廃止する。

## Problem and outcome

- 今は、実行順が計画のどこにも図や一覧として示されていない。計画をレビューするときに「何が同時に走れて、何を待つのか」を頭の中で組み立てる必要がある。
- `board next` は並列グループを単位に一斉に進めるので、依存先が終わって着手できるタスクがあっても、別のグループが走っている間は始められない。待ち時間が積み重なる。
- ボードは状態ごとの列とリストで進捗を見せる。しかし、依存関係の流れの中で今どこまで進んでいて、何が後続を止めているのかは見えない。

これにより、ユーザーは計画のレビューの段階で実行の流れを図で確かめてから承認できる。実装中は、着手できるタスクが待たされることなく始まり、同じ図の上で進み具合とボトルネックを把握できる。

## Target users

- Smartpowers で計画をレビューして承認するユーザー
- 実装中の進捗をボードで見守るユーザー
- 着手するタスクを決めてサブエージェントに割り振るリードエージェント

## Scope

### In scope

- 実行計画を依存関係のグラフとして表す計画の書式と、計画ガイドの変更(並列グループの廃止を含む)
- `validate_workflow.sh --phase plan` による依存関係のグラフの検査
- `board next` コマンドの廃止
- 依存関係に基づいて逐次に着手する、リードエージェントの手順(`SKILL.md`)
- ボードのフローチャート表示(依存の矢印、状態のライブ表示、着手できるタスクの表示、クリックで詳細、Draft の計画の表示)

### Out of scope

- ボード上で依存関係やタスクの状態を編集すること(今までどおりファイルが正)
- Mermaid などの外部の図のライブラリや、Markdown の中の図の記法
- 着手するタスクを自動で選んで出力するコマンド(リードが自分で判断する)
- 同時に走らせるサブエージェントの数の上限を、仕組みとして設けること
- 完了済みの既存プロジェクトのタスクファイルを書き換えること
- Crit のレビューと PR(parallel-review-pr プロジェクト)

## Functional requirements

| ID | Priority | Requirement | Acceptance criteria |
| --- | --- | --- | --- |
| REQ-001 | Must | 実行計画は、各タスクの `Depends on` が表す依存関係のグラフとする。計画ガイドは、計画を作るときに、同時に進めると衝突するタスク(担当するファイルが重なるもの、移行の順序があるもの)の間に必ず依存を張るよう指示する。依存のないタスク同士は、同時に進めてよいことを意味する。 | 計画ガイドに、依存の張り方の規則と、依存のないタスクは同時に走りうることが書かれている。 |
| REQ-002 | Must | 並列グループを廃止する。計画ガイドの `PLAN.md` の表とタスクファイルの書式から `Parallel group` を除き、`SKILL.md` やボードの説明からも除く。既存のタスクファイルに残っている `Parallel group:` の行は無視する。 | 計画ガイドと `SKILL.md` に並列グループの記述がない。`Parallel group:` の行がある既存のプロジェクトも、検査とボードでエラーにならない。 |
| REQ-003 | Must | `validate_workflow.sh --phase plan` は依存関係のグラフを検査する。依存先のタスクが存在すること、循環がないこと、`PLAN.md` の表の `Depends on` がタスクファイルと一致することを確かめる。 | それぞれの違反を含む計画で検査が失敗し、違反したタスクを示すメッセージが出る。正しい計画では成功する。 |
| REQ-004 | Must | `board next` コマンドを廃止し、その実装、テスト、説明を取り除く。 | `board next` を実行すると、未知のコマンドとしてエラーになる。`SKILL.md` に `board next` の記述がない。 |
| REQ-005 | Must | `SKILL.md` の並列実行の手順を、依存関係に基づく逐次の着手に変える。リードは、状態が `Planned` で依存先がすべて `Done` のタスクを自分で見つけ、着手できるものにはすぐにサブエージェントを割り当てる。サブエージェントが 1 つ終わってタスクが `Done` になるたびに、新たに着手できるようになったタスクを探して始める。ほかのタスクの完了を待って一斉に始めることはしない。 | `SKILL.md` に、着手できるタスクの条件、完了のたびに見直す手順、一斉に待たないことが書かれている。 |
| REQ-006 | Must | リードは、走っているタスクと担当するファイルが重なりそうなタスクを見つけたら、依存がなくても同時には始めない。その判断をログに残し、計画の不備としてユーザーに伝える。 | `SKILL.md` に、この場合の扱いが書かれている。 |
| REQ-007 | Must | ボードに、ボード表示とリスト表示に並ぶ 3 つ目の表示としてフローチャートを加える。タスクをノード、依存を矢印で描き、依存の深さに応じて左から右へ並べる。 | 依存のあるプロジェクトで、各タスクが依存先より右に描かれ、`Depends on` の数だけ矢印がある。 |
| REQ-008 | Must | フローチャートのノードは、タスクの状態(Planned / In Progress / Blocked / Done)で見分けがつき、タスクファイルが変わるとリロードなしで更新される。エージェントが接続しているタスクにはその表示を出す。 | `Status:` を書き換えると、約 1 秒の監視間隔の範囲でノードの表示が変わる。接続中のタスクには Agent の表示が出る。 |
| REQ-009 | Must | `Planned` で依存先がすべて `Done` のタスクは、着手できるタスクとしてフローチャートで見分けられるようにする。 | 依存先が最後に `Done` になったとき、後続のノードが、リロードなしで着手できる表示に変わる。 |
| REQ-010 | Must | ノードをクリックすると、既存の詳細パネルが開く。URL で、フローチャートの表示と選んだタスクを直接開ける。 | ノードのクリックで、そのタスクの詳細パネルが開く。URL を開き直すと、同じ表示とパネルが復元される。 |
| REQ-011 | Must | 計画が `Status: Draft` の間もフローチャートを表示し、承認前のレビューに使えるようにする。 | Draft の `PLAN.md` と、`Planned` のタスクファイルだけのプロジェクトで、フローチャートが表示される。 |
| REQ-012 | Should | 依存関係に問題があるとき(存在しないタスクへの依存、循環)は、ボードは表示を止めずに、問題を表示上で示す。 | 循環を含むプロジェクトで、フローチャートの上に警告が出て、ほかの表示は今までどおり動く。 |
| REQ-013 | Should | キーボードでフローチャートに切り替えられる。 | 入力欄にフォーカスがないとき、`f` でフローチャートの表示になる(`b` と `l` は今までどおり)。 |
| REQ-014 | Must | フローチャートは、開いたときに図全体を表示エリアの中央に、エリアに収まる最大の大きさで描く。ホイールで拡大縮小、背景のドラッグで移動ができ、「全体表示」のボタンで最初の表示に戻せる。ライブ更新で描き直しても、拡大率と位置は保つ。 | 5 タスクの計画でも 30 タスクの計画でも、開いた直後に図全体がエリアの中央に収まる。拡大と移動のあとにタスクファイルを編集しても、表示の位置が変わらない。 |
| REQ-015 | Should | ノードの縦の位置は格子に揃えず、依存先と後続の中ほどに寄せて、矢印がなるべくまっすぐになるようにする。左から右への流れ(依存の深さによる列)は保つ。 | 依存先が 1 つだけのタスクは、依存先とほぼ同じ高さに描かれる。後続のタスクは、つねに依存先より右にある。 |
| REQ-016 | Should | 見た目を整える。ノードの左端に状態の色の帯を付け、背景にドットの格子を敷く。ノードにマウスを乗せるかフォーカスすると、そのノードにつながる矢印を強調し、ほかを薄くする。同じ隙間を通る長い矢印は、少しずつずらして 1 本に重ならないようにする。 | 状態ごとに帯の色が違う。ノードにマウスを乗せると、つながる矢印だけが濃く表示される。3 本の長い矢印が同じ隙間を通るとき、3 本が見分けられる。 |

## Non-functional requirements

| ID | Area | Requirement | Measure |
| --- | --- | --- | --- |
| NFR-001 | Maintainability | 図は外部のライブラリを使わず、ビルド工程のない ES モジュールと SVG で描く。サーバーは std のみの Rust のままにする。 | 新しい依存(npm、CDN、crate)が増えていない。 |
| NFR-002 | Consistency | 依存関係のグラフの解釈(着手できるか、深さ、循環)は、ボードのサーバーの 1 か所で計算し、API でフロントへ渡す。 | フロントは配置と描画だけを行い、着手できるかどうかを独自に判定していない。 |
| NFR-003 | Scale | 30 タスク程度の計画でも、ノードが重ならずに読める。 | 30 タスク・深さ 8 の計画で、ノードが重ならない。開いた直後は図全体がエリアに収まり、拡大すれば各ノードの文字が読める。 |
| NFR-004 | Accessibility | ライト/ダークの両方で、ノードの文字色がコントラスト比 4.5:1 以上になる。状態と着手できることは、色だけでなくラベルかアイコンでも区別できる。 | 配色の組み合わせのコントラスト比を計算して確認する。 |
| NFR-005 | Safety | ボードは今までどおり、リポジトリのファイルを変更しない。 | フローチャートの追加で、リポジトリへの書き込みが増えていない。 |

## User journeys

1. エージェントが計画の草案を書く。02 と 03 は 01 に依存し、04 は 02 だけに依存する。ユーザーはボードのフローチャートで流れを確かめ、03 と 04 が同じファイルに触れることに気づいて、03 → 04 の依存を足すようフィードバックする。
2. 計画が承認される。リードは 01 に着手する。01 が `Done` になると、フローチャートで 02 と 03 が着手できる表示に変わり、リードは 2 つのサブエージェントを同時に起動する。
3. 02 が先に終わる。リードは 03 の完了を待たずに、04 を着手できると判断してすぐに始める。ユーザーは、03 が長引いていることをフローチャートで見て、ノードをクリックしてログを読む。

## Assumptions and constraints

- 同時に進めてよいかどうかは、依存関係のグラフだけで表す。並列グループで表していた「担当するファイルが重ならない」という条件は、計画を作るときに依存として張る。
- 着手できるタスクを選ぶのはリードエージェントの判断で、それを支える専用のコマンドは設けない。リードはタスクファイルの `Status:` と `Depends on:` を読んで判断する。
- 完了済みの既存プロジェクトは検査し直さない。ボードでは、それらの依存関係をそのままフローチャートに描く。
- 対象は、既存のボード(Rust のサーバーと、埋め込みの ES モジュールの UI)、bash の検証スクリプト、`SKILL.md` と計画ガイドである。
- `board next` の廃止は互換性のない変更なので、CHANGELOG に記載する。

## Success measures

- 計画のレビューで、ユーザーが Markdown の表を読まなくても、同時に走れるタスクと待ちの関係をフローチャートで確かめられる。
- 実装中に、依存先がすべて `Done` になったタスクが、ほかのタスクの完了を待たされずに着手される。

## Risks

- 並列グループというはっきりした区切りがなくなるため、計画の段階で依存の張り忘れがあると、同じファイルを同時に変更してマージで衝突する。REQ-006 のリードの判断と、レビューでの図の確認で補う。
- 着手の判断をエージェントに任せるので、決まった規則のコマンドよりも判断がぶれる可能性がある。
- 自前のレイアウトでは、矢印の交差が多い計画で図が読みにくくなる可能性がある。
